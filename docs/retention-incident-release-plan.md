# Согласование восстановления Retention

## Область изменения

Только MANA AI на сервере `209.38.78.125`: API, admin UI и operation worker.
Не менять SSH, Firebase rules, документы Firebase, другие проекты или существующие ключи.
Новый read-only service account предназначен только для авторизованного чтения; выдавать ему
дополнительные права, подключать GA4 или запускать массовые выгрузки в этот релиз не входит.

Production-действия и контрольные чтения выполняются после согласования этого плана с командой.
Локальные тесты используют fake/mock провайдеры и не обращаются к платным API.

## Зафиксированное исходное состояние

При read-only проверке 28 сентября 2026 года около 11:23 UTC Docker-контейнеров на сервере не было;
nginx продолжал работать, но порты приложений 8000 и 3000 не слушались. Пользователь сообщил,
что контейнеры, вероятно, намеренно удалили после инцидента.

Сохранились тома `mana-ai_manaai_postgres`, `mana-ai_manaai_data` и резервные копии
`/var/backups/mana-ai/`. Это не подтверждает целостность БД: её необходимо проверить отдельно.
Git checkout в `/opt/manaai-api` указывал на `d96c227763aadb28d6ef6da005a39feffba2f2cd`;
runtime-каталог `/root/mana-ai` не является Git checkout.

Нельзя выдавать восстановление ранее отключённого приложения за zero-downtime обновление.
Перед действиями повторно проверить состояние: другие разработчики могли восстановить сервис.

## Предлагаемые шаги

1. **Подтвердить согласование и текущее состояние.** Зафиксировать согласованный commit SHA,
   контейнеры, образы, домены, состояние расписания и health. Если сервер уже восстановлен,
   сохранить его актуальные настройки и выбрать безопасное переключение без остановки клиентов.
2. **Сделать резервную копию.** Сохранить существующие тома и конфигурацию с ограниченными правами
   доступа, проверить копию. Не создавать пустую БД вместо сохранившейся и не удалять старые тома.
3. **Собрать точный запушенный commit.** Сверить SHA checkout и образов. Подготовить rollback на
   предыдущую конфигурацию/образы, но с Retention выключенным: нельзя вернуть аварийный polling.
4. **Поднять базу и проверить состояние.** Использовать существующий PostgreSQL-том, сверить
   миграции и наличие данных. Не запускать старый worker. Сохранить Retention schedule выключенным;
   сначала оставить scheduler выключенным на уровне процесса. Новый релиз не требует новой
   миграции: поля защиты совместимы с существующими JSON payload расписаний.
5. **Подключить предоставленный ключ.** Разместить JSON вне Git и образов с правами `0600`,
   смонтировать read-only, указать `FIREBASE_SERVICE_ACCOUNT_FILE`, отключить
   `FIREBASE_PUBLIC_READ_ENABLED`. Не менять правила или IAM-роли. При отказе доступа остановиться,
   а не расширять права и не переходить молча на публичный доступ.
6. **Восстановить API и admin UI.** Проверить liveness, авторизацию, домены/TLS и совместимость
   существующих endpoint-контрактов. Не использовать страницы integration health как бесконечный
   smoke-test: некоторые проверки сами читают внешние источники. Не вызывать реальный OpenAI
   ради Retention-canary.
7. **Один ограниченный canary.** Оставить автоматическое расписание выключенным. Использовать
   только Manakids и operational Firestore, один документ на коллекцию, общий предел пять
   запрошенных документов, пять страниц и пять Firestore HTTP-попыток. Выключить transport retry,
   ограничить Manakids одной страницей на endpoint. Один раз выполнить анализ с уникальным ключом,
   затем повторить тот же ключ и проверить отсутствие новых запросов. При любой ошибке остановиться.
8. **Проверить доказательства.** Зафиксировать run ID, статус, audit, итоговые счётчики обращений
   по provider/endpoint, полученные документы отдельно от зарезервированного верхнего предела,
   отмену незавершённых задач и неизменность счётчиков при повторе ключа. Счётчики приложения
   не выдавать за фактическую выписку Google Billing.
9. **Вернуть расписание только после успешной проверки.** Сохранить малый проверенный бюджет
   на первый контрольный цикл; включить `20 */6 * * *` UTC и наблюдать до выполнения следующего
   штатного запуска и последующих polling-проверок. Убедиться, что occurrence выполнена однократно,
   `next_run_at` находится в будущем, бюджет соблюдён и сервис остаётся здоровым. Увеличение размера
   выборки согласовывается отдельно, поскольку оно увеличивает чтения и расходы.
10. **Отчёт или остановка.** Сообщить commit/deployment SHA, результаты тестов, проверок и счётчики
    canary/контрольного цикла. При провале оставить Retention выключенным, сохранить диагностику,
    при необходимости откатить приложение без повторного включения проблемного сборщика.

## Что исправляет релиз

- Однократное обновление Manakids token при 401/403; повторный отказ не повторяется транспортом.
- Отмена и ожидание завершения параллельных задач на всех уровнях сбора.
- Атомарное потребление occurrence до внешних запросов; конечные transient retry и перенос слота
  после ошибки. Пропущенные исторические слоты не догоняются массовыми чтениями.
- Терминальные failed-run не переоткрываются с тем же ключом.
- Сохранённый circuit breaker, audit/alert и защита от сброса отключения устаревшими настройками.
- Общий бюджет Firestore для всех источников одного run, включая retry и неопределённые результаты.
- Privacy-safe HTTP-счётчики и отдельные показатели возвращённых документов и резервирования.

Наличие этих изменений и локальных тестов не означает, что production-canary уже выполнен.
Исторические расходы требуют отдельной сверки Billing; приблизительную реконструкцию нельзя
считать подтверждением ни суммы около $65, ни суммы $250.
