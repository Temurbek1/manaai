# MANA — один чат родителя в приложении

Новая отдельная возможность `mana-ai`, не чат администрации и не OPERATION Goals.
Один канонический ID родителя означает одну историю. Создания дополнительных чатов,
выбора модели пользователем, инструментов и действий над детьми нет.

## Вызов через backend приложения

Мобильное приложение обращается к своему backend с обычной пользовательской
авторизацией. Backend **сам** определяет `Parent.id` вошедшего родителя и обращается
к этому сервису с серверным `APP_API_KEY`. Ключ нельзя включать в мобильную сборку.
Нельзя просто пересылать произвольный `parent_id`, полученный с телефона: наш
серверный ключ аутентифицирует backend, а не конкретного родителя.
Ключ этого экземпляра должен быть доступен только доверенному MANA backend. Если
он общий с 360REC, мобильными клиентами или другими интеграциями, перед включением
персонального чата нужно разделить экземпляр/ключи: общий inference-ключ сам по себе
не является подтверждением права на персональную историю.

`parent_id` — строка с каноническим положительным числовым ID профиля,
совпадающим с ID родителя в Firebase и `Parent.id` документированного MANA Parent API.
Это **не Firebase Auth UID**, не телефон и не ID аккаунта администратора. Значения
с ведущими нулями, путями или префиксами отклоняются, чтобы не создавать чаты-дубликаты.
ID нельзя переиспользовать для другой учётной записи; файл истории нельзя разделять
между production/staging или разными MANA-инсталляциями с совпадающими числовыми ID.
Если ID профиля и ID документа различаются, backend должен сделать подтверждённое
сопоставление, а не подставлять UID или угадывать номер.

```bash
curl 'http://127.0.0.1:8000/api/v1/mana-ai/chat?parent_id=123&limit=30' \
  -H "Authorization: Bearer ${APP_API_KEY}"

curl 'http://127.0.0.1:8000/api/v1/mana-ai/chat' \
  -H "Authorization: Bearer ${APP_API_KEY}" \
  -H 'Content-Type: application/json' \
  -d '{"parent_id":"123","request_id":"8270fbd2-1579-4c44-955c-6703ac27098f","message":"Как помочь ребёнку со сном?"}'
```

Примеры выше локальные. Endpoint выпущен отдельно; фактические проверки и границы
зафиксированы в [mana-parent-chat-release.md](mana-parent-chat-release.md).
Для изолированного production-развёртывания используйте тот же путь на
`https://ai.360rec.uz` с **отдельным ключом MANA чата**. В Swagger он называется
`ParentChatBackendToken`; старый `BearerToken` остальных inference endpoints
не даёт доступа к переписке. `docker-compose.parent-chat.yml` запускает отдельный
сервис и постоянный volume. Nginx-snippet `deploy/nginx/mana-parent-chat.conf`
маршрутизирует только точный `/api/v1/mana-ai/chat`, не меняя остальные API/аудио.
Конкретные результаты выпуска фиксируются отдельно, не выводятся из примеров.

POST возвращает `answer`, `model`, `usage.input_tokens`, `usage.output_tokens`,
`quota`, количество прошлых пар, включённых в контекст, и время чтения профилей.
При идемпотентном повторе POST возвращает исходный снимок квоты; актуальная квота
доступна в GET. Backend должен сохранить ID и тело запроса до отправки, связав их
с тем же пользовательским намерением при повторе между телефоном и backend.
Язык и письменность ответа задаются последним сообщением, без фиксированного выбора
RU/UZ. Смешанный текст использует основной язык. Это инструкция модели, а не
детерминированная гарантия перевода любого текста.
Сообщение обязательно, не может состоять из пробелов и ограничено 2000 символами;
это отдельное ограничение размера, не дневная квота токенов.

GET возвращает `messages`, актуальную квоту, последний `request_id`/статус/код
ошибки и `next_before_turn_id`. Внутри страницы сообщения идут от старых к новым;
для более старой страницы передать `before_turn_id=next_before_turn_id`.
`limit` ограничивает пары сообщений (до 100), а не число отдельных сообщений.
GET не вызывает модель, Parent API, GA4 или Firebase. Для UI достаточно загрузки
истории и отправки сообщения; никакие дополнительные чаты создавать не нужно.
История и ответы помечены `Cache-Control: no-store`.

## Данные ребёнка и фактическое покрытие

На каждый **новый** POST делается строго отфильтрованный запрос:

`GET /api/v1/admin-panel-parent/parent-list/?parent_id=<ID>&limit=1&offset=0`.

Проверяются точный ID, единственный результат, полнота и отсутствие дубликатов
детей. Нельзя переходить по `next`, читать все семьи или использовать чужие ID из
сообщения. При ошибке/неподтверждённой привязке модель не вызывается. При истёкшем
токене текущий запрос не повторяется; последующая отдельная попытка может заново
авторизоваться после cooldown. 403 не вызывает цикл авторизаций.

Из профиля модели доступны только имена, известный детский возраст и состояние
привязки. Нулевой/недетский возраст считается неизвестным; `is_connected` не означает
«ребёнок сейчас онлайн». Телефоны, родительский профиль, тарифы, аватары, учётные
данные и реальные ID детей модели не передаются.

Backend может дополнительно передать `child_observations` (не больше одной на
ребёнка). Каждый ID проверяется по **свежему списку подключённых детей**. Например:

```json
{
  "parent_id": "123",
  "request_id": "0175b3a9-68b2-4876-b91d-61448c94f6bb",
  "message": "Он слишком много сидит в телефоне?",
  "child_observations": [{
    "child_id": 456,
    "observed_at": "2026-10-16T12:00:00Z",
    "battery_percent": 42,
    "screen_time_minutes": 120,
    "activity_period_start": "2026-10-16T00:00:00Z",
    "activity_period_end": "2026-10-16T12:00:00Z",
    "apps": [{"app_name": "Example game", "minutes": 45}]
  }]
}
```

Поддерживаются заряд, краткая метка места, экранное время и до пяти приложений
с длительностью. Для активности обязательны начало/конец периода; время чтения
базы не заменяет фактическое время наблюдения. Не допускаются будущие наблюдения
за пределами пятиминутного допуска часов, интервалы свыше 31 дня и длительность
одного показателя больше интервала. Старые данные не превращаются в текущие.

**Прямого загрузчика GPS, звонков, активности или телеметрии из Firebase здесь нет.**
Эти поля загружает и минимизирует backend приложения, уже владеющий пользовательской
авторизацией. Без них модель видит только профили и переписку и должна сообщать о
нехватке фактов, не придумывать анализ поведения. Чат не читает административные
отчёты, другие семьи, 360REC, GA4 и полные коллекции Firestore. Ни одного нового
расписания, listener или автообновления не создаётся.

## Квоты, повторы и ошибки

- По умолчанию **5000 входных + выходных токенов на родителя в сутки**. Системная
  инструкция, данные ребёнка и предыдущие сообщения тоже входят в расход;
  cached input учитывается полностью, reasoning уже входит в output. Это не
  2000 символов, не 5000 токенов ответов и не фиксированное число сообщений.
- Сброс в полночь `Asia/Tashkent`, часовой пояс настраивается. GET возвращает
  точное `resets_at`. Максимум ответа — 512 токенов, уменьшается под остаток.
- Перед генерацией вызывается официальный input-token count с теми же моделью,
  инструкцией и входом. Если старые пары не помещаются в остаток, они целиком
  исключаются из модельного контекста и выполняется один дополнительный count.
  Текущий вопрос и факты ребёнка не сокращаются; в SQL все сообщения остаются.
  Итого максимум два sizing-вызова и одна генерация. Ошибка count не повторяется.
  Если и без старых пар на ответ не остаётся хотя бы 32 токена, генерации нет.
  Подход основан на [официальном контроллере расходов Responses API](https://developers.openai.com/cookbook/articles/per_run_spending_controller_responses_api).
  Здесь лимит в токенах, не расчёт USD; стоимость count endpoint отдельно не проверялась.
- Вся история хранится в SQL; модели передаются только **две последние успешные
  пары** по умолчанию, либо ни одной, когда они не помещаются в квоту. Ответ содержит
  фактическое `history_turns_included`. Старые сообщения доступны через GET. Автоматического
  платного сжатия, суммаризации и обещания бесконечной памяти нет.
- Резерв и единственный активный запрос фиксируются в короткой SQL-транзакции
  **до** источника/модели. Защита работает между процессами, не только в памяти.
- На родителя допускается 20 новых попыток в сутки, включая неуспешный preflight.
  Это отдельная защита от повторных чтений и вызовов count. Дополнительно действуют
  существующие IP/auth rate limits.
- `request_id` создаётся один раз для намерения. При потере HTTP-ответа нужно
  повторить **тот же ID и тело**, включая наблюдения. Успешный повтор возвращает
  сохранённый ответ без нового чтения и генерации. Другое тело с тем же ID: 409.
- 409 `request_in_progress`/`previous_request_unresolved`: смотреть GET, не
  создавать новый ID для автоматического повтора. GET ничего не перезапускает.
- Потерянный/нетерминальный/невалидный usage после отправки модели оставляет
  долговечный резерв, блокирующий последующие вызовы даже после полуночи и
  перезапуска. Автоповтора и автоматического «возврата» токенов нет. Требуется
  ручная сверка владельцем сервиса; публичного reset/unblock endpoint нет.
- Незавершённый ответ с валидным терминальным usage оплачивается токенами,
  но не публикуется как готовый ответ (502). Usage учитывается до разбора текста.
  Подтверждённый reject до inference освобождает резерв; таймаут/5xx/неизвестный
  результат — нет. Автоматические повторы SDK/HTTP выключены.
- Подготовка, не дошедшая до отправки модели за пять минут, может быть завершена
  отказом без платной генерации. Старый процесс после этого не может отправить
  освобождённую заявку. Отправленная заявка этим правилом не освобождается.

## Включение и хранение

По умолчанию `MANA_PARENT_CHAT_ENABLED=false`; даже в локальном режиме персональный
чат требует серверный ключ. Включение требует:

```dotenv
MANA_PARENT_CHAT_ENABLED=true
MANA_PARENT_CHAT_DATABASE_PATH=data/mana-parent-chat.sqlite3
MANA_PARENT_CHAT_DAILY_TOKENS=5000
MANA_PARENT_CHAT_TIMEZONE=Asia/Tashkent
MANA_PARENT_CHAT_MAX_OUTPUT_TOKENS=512
MANA_PARENT_CHAT_HISTORY_TURNS=2
MANA_PARENT_CHAT_MAX_ATTEMPTS_PER_DAY=20
MANA_PARENT_CHAT_SOURCE_TIMEOUT_SECONDS=30
```

Также нужны `APP_API_KEY` (не менее 32 символов), `OPENAI_API_KEY`, существующие
`MANAKIDS_API_BASE_URL`, `MANAKIDS_API_USERNAME` и `MANAKIDS_API_PASSWORD`.
Модель остаётся настраиваемой через `OPENAI_MODEL`; отдельной скрытой смены модели нет.
Чтение источника ограничено общим wall timeout (30 секунд по умолчанию).
SDK timeout модели берётся из `OPENAI_TIMEOUT_SECONDS` с потолком 120 секунд;
общий wall timeout каждого модельного/count вызова — ещё +10 секунд, без повторов.
Дневной период фиксируется при приёме сообщения: пересечение полуночи во время
вызова не переносит его резерв/расход в новый день. GET показывает текущий день.

Хранилище — отдельный versioned SQLite/WAL файл с короткими транзакциями и правами
нового файла 0600; raw наблюдения не сохраняются, только digest исходного запроса,
тексты сообщений/ответов и результат/квоты. Каталог нового хранилища создаётся 0700.
Не указывать operation/marketing DB или `:memory:`. Схема операции не мигрируется.
Приложение не удаляет историю и не применяет автоматическую retention-политику.
Доступ, срок хранения, удаление по запросу владельца и шифрование диска/backup должны
быть согласованы для реальных детских данных до эксплуатации.

`docker-compose.mana-ai.yml` монтирует отдельный durable volume `/app/data`;
основной compose использует существующий `/data` volume с отдельным файлом.
Все API workers должны работать **на одном хосте с одним локальным файлом**;
нельзя использовать отдельные ephemeral-файлы реплик или SQLite на сетевом диске.
Для multi-host deployment нужен другой адаптер того же typed store port.
Backup/restore — штатный SQLite backup с согласованным WAL, не копирование одного
живого `.sqlite3` файла. Восстановление старого backup не является безопасным
откатом приложения: оно может потерять историю и резервы.

Модель вызывается с `store=false`; это не обещание нулевого хранения у провайдера.
Чат не исполняет действия, не диагностирует заболевания и не заменяет экстренную
помощь. Мобильный клиент должен безопасно отображать текст, не исполнять HTML/ссылки
или команды из ответа модели. Production, SSH, ключи, расписания и данные источников
этой локальной реализацией не изменяются.
