## A reproduced dispatch-boundary defect

The continuation finisher checked that raw output had one selected function, but
not that it survived pruning as an exact, still-pending invocation. Three synthetic
regressions failed before the fix: invocation before the latest compaction, a
provider-supplied tool result consuming the invocation, and a different typed call.
These are reproduced protocol defects, not evidence that production encountered
them or the cause of any historical cost incident.

The finisher now checks retained invocation ID, canonical typed arguments and
pending status before returning a dispatchable decision. Provider output cannot
attach runtime/SQL tool receipts. Valid server compaction and runtime-supplied
completed tool outputs remain supported; existing pairing logic is shared rather
than duplicated. No provider items are reordered and opaque content is not decoded.

Malformed continuation stops **before tool dispatch**, with verified usage retained
as priced cost. It does not enter the two-step decision-format correction lane,
refund a hold, repeat a source/model request or infer approval. Two SDK/application/
SQL regressions verify waiting state, zero tools/execution, original request, exact
cost and no automatic second tick. Private protocols/schema/flags are unchanged.

[Official server-side compaction guidance](https://developers.openai.com/api/docs/guides/compaction#server-side-compaction)
supports appending response items and pruning before the latest actual compaction
item; it does not make an absent function invocation or a model-generated result an
authoritative executable receipt. The runtime additionally reasserts complete user
conditions and saved evidence independently of opaque provider memory.
