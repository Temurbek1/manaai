# Конверсия MANA: какие события нужны от backend

Контракт локальной реализации после `863bc06`, не инструкция включения production.
Новые conversion/proactive endpoints пока не выпущены. Действующий production
`f8d095e` не обновлялся этой документацией. Полная цель — наблюдать всех родителей
MANA и вовремя предлагать переход с бесплатного доступа на платный через один
Parent-Touch. Сейчас готов приём событий, но реальный producer этих событий ещё
не подключён. Агент не создаёт платежи или транзакции.

## 1. Что сделать backend-разработчику

1. Из своих авторитетных таблиц подписок, согласий и активности собрать полный
   `ConversionSnapshot` для каждого родителя MANA. Включить и родителей, которые
   ещё не писали в чат. Не переносить сюда семьи 360REC.
2. Сохранить событие в transactional outbox backend вместе с изменением данных.
   Передать его в `POST /api/v1/mana-ai/conversion-agent/events`.
3. При оплате, выдаче/окончании бесплатного доступа, смене настроек или новой
   активности передать новое текущее состояние с большей `revision`.
4. Для временных рубежей — например, седьмого дня — backend должен перечитать
   собственное состояние в нужный момент и передать свежий snapshot. Одного
   события при регистрации недостаточно: AI-сервис не перечитывает Firebase
   автоматически и не освежает старое наблюдение изменением его даты.
5. До исходящего обращения зарегистрировать подтверждённые язык и контактные
   настройки. После реальной оплаты передать актуальный `subscription="paid"`;
   отдельно привязать платёж к опубликованному предложению, если он ему относится.

Для начального охвата нужен согласованный одноразовый export всех родительских
аккаунтов из backend с контрольным числом записей и идентификаторами пропусков.
Далее — изменения, рубежи времени и контроль потерь событий через outbox.
Это требование к ещё не реализованному producer, а не разрешение на массовое
сканирование Parent List/Firebase из AI-сервиса. «Наблюдать всех» не означает
«посылать предложения всем»: consent, приоритет safety, caps и cooldown сохраняются.

## 2. Существующие локальные endpoints

Во всех запросах backend использует отдельный серверный bearer родительского
AI-сервиса. Он не передаётся телефону. `parent_id` определяется по профилю MANA:
числовой `Parent.id` строкой, не телефон, ID ребёнка или Firebase Auth UID.

```http
Authorization: Bearer <ISOLATED_MANA_PARENT_CHAT_BACKEND_TOKEN>
Content-Type: application/json
User-Agent: MANA-Backend/1.0
```

| Метод и путь после `/api/v1/mana-ai` | Назначение |
| --- | --- |
| `POST /conversion-agent/events` | `ConversionSnapshot`; ответ `202 ConversionAdmission` |
| `GET /conversion-agent/proposals?parent_id=123&after=0&limit=20` | История предложений, только SQL |
| `GET /conversion-agent/proposals/{proposal_id}?parent_id=123` | Одно предложение, только SQL |
| `POST /conversion-agent/outcomes` | Реакция родителя или подтверждённая оплата; `ConversionOutcome` |
| `POST /parent-touch/contact-context` | Язык, timezone, раздельные согласия; `ParentContactContext` |
| `GET /parent-touch/contact-context?parent_id=123` | Сохранённые контактные настройки |
| `GET /parent-touch/chat?parent_id=123&limit=30` | Единственный чат с сообщениями Parent-Touch |
| `GET /parent-touch/notifications?parent_id=123&after=0&limit=20` | Квитанции push, не доставка |
| `POST /conversion-agent/trial-acceptances` | Явное согласие на бесплатные дни; `TrialAcceptance` |
| `GET /conversion-agent/trial-grants?parent_id=123` | Состояние бесплатной выдачи, без повторного вызова провайдера |

Выключенный conversion runtime отвечает `503 conversion_agent_disabled`;
proactive — `503 parent_proactive_disabled`; выдача дней — `503 trial_grants_disabled`.
`GET` не отправляет сообщения, не читает внешние источники и не запускает модель.
`decision` и `proposal` в admission нужно сохранить: `queued` — ещё не опубликованный
оффер. Само сообщение публикует только worker Parent-Touch, не вызывающий backend.

## 3. Откуда должны взяться поля snapshot

| Поля | Нужное происхождение; что нельзя подставлять |
| --- | --- |
| `product`, `parent_id` | Только MANA и канонический `Parent.id`; связь аккаунта проверяет backend |
| `event_id`, `revision` | Неизменяемый UUID события и возрастающая версия состояния конкретного родителя |
| `observed_at` | Время фактической проверки полного состояния, не дата отправки старого кэша |
| `subscription` | Авторитетная классификация `free`, `paid`, `expired`, `unknown` по подпискам и факту оплаты, не по названию тарифа |
| `free_started_at` | Реальное начало бесплатного использования; для `free` обязательно. Не дата регистрации или первого чата без доказанной эквивалентности |
| `free_access_ends_at` | Реальное окончание бесплатного доступа, если оно известно; `null` не означает бессрочный доступ |
| `agent_trial_given` | История одной пожизненной выдачи agent-тарифа: `false` только при доказанном отсутствии, иначе `true` или `null` |
| `marketing_consent`, `consent_observed_at` | Отдельное подтверждённое согласие на маркетинговое общение и время его проверки; не OS-permission, использование приложения или согласие на safety |
| `language`, `timezone` | Настройки родителя: `ru`, `uz-Latn`, `uz-Cyrl`, `en` и IANA timezone; не язык ребёнка и не догадка по стране |
| `last_active_at` | Фактическое время последней родительской активности |
| `active_days_7d`, `sessions_7d`, `paywall_views_7d` | Проверенные агрегаты именно родителя за последние семь дней до `observed_at`; определение сессии/дня/экрана оплаты согласовать с владельцем событий |

Согласовать у владельца billing точное правило при пересекающихся entitlement:
действующий оплаченный доступ нельзя классифицировать `free` из-за параллельной
бесплатной записи. Отсутствие текущего тарифа не доказывает `free` или отсутствие
прошлой agent-выдачи. Неизвестные факты не заменять выдуманными датами/нулями/согласием.
Если обязательных проверенных полей нет, такой аккаунт ещё не готов к контактному
потоку; список пробелов должен остаться в backend-аудите.

Существующий payload **не имеет** полей `source`, `evidence`, `is_paid` или списка
источников: добавлять их в JSON нельзя (`extra="forbid"`). Producer должен отдельно
сохранить проверяемое соответствие полей своим таблицам/API, версии агрегации,
время чтения и связь `event_id` с исходным изменением. Серверный bearer доверяет
этим утверждениям backend; валидный JSON сам по себе не доказывает их истинность.

### Пример snapshot: семь дней бесплатного использования

Все ID, даты и офферы ниже вымышленные; примеры проверены только по локальным
типизированным моделям. Они не дают разрешения на контакт и не являются пакетами
для реальной отправки. При отправке нужны реальные свежие факты, не сдвинутые даты.

```json
{
  "product": "mana",
  "parent_id": "123",
  "event_id": "7ceea1bf-b4b4-48ac-a12b-9f7c7d6e5c11",
  "revision": 1,
  "observed_at": "2026-10-21T09:00:00Z",
  "subscription": "free",
  "free_started_at": "2026-10-14T09:00:00Z",
  "free_access_ends_at": "2026-10-22T09:00:00Z",
  "agent_trial_given": false,
  "marketing_consent": true,
  "consent_observed_at": "2026-10-21T09:00:00Z",
  "language": "uz-Latn",
  "timezone": "Asia/Samarkand",
  "last_active_at": "2026-10-21T08:50:00Z",
  "active_days_7d": 3,
  "sessions_7d": 5,
  "paywall_views_7d": 1
}
```

### Свежесть и повторная доставка

- По умолчанию snapshot пригоден для контакта **900 секунд**; допустимый параметр
  `snapshot_max_age_seconds` — 60–3600. Просроченные данные не разрешают оффер.
- Новый snapshot требует `revision > предыдущей`, а `observed_at` — не раньше
  предыдущего. Будущее более чем на 120 секунд отклоняется. Датировка бесплатного
  доступа и активности не может быть позже времени наблюдения.
- При потере HTTP-ответа outbox повторяет тот же `event_id` и неизменённое тело:
  сервис возвращает первоначальную квитанцию. Другой payload с тем же ID — `409`.
  Новый UUID не используется для обхода отказа или повторной отправки push/выдачи.
- Новый snapshot закрывает ещё не опубликованное старое предложение и заново
  проверяет допустимость. Более новая версия с `paid`/без согласия должна попасть
  в AI-сервис без задержки; оплата только во внешнем backend до получения события
  сервису неизвестна. Проверки локального snapshot — не live-запрос в billing.
- Начальный export, растянутый на часы, не делает все его записи свежими к концу.
  Нужны реальные текущие проверки в producer непосредственно перед событием.
  Нельзя заменить это частым полным чтением Firestore или фиктивным `observed_at`.

Сейчас eligibility детерминирован: подтверждённый `free`, marketing consent,
активность за семь дней и последний визит не старше двух дней; затем либо минимум
семь суток бесплатного использования, либо минимум сутки + два активных дня +
три сессии + один просмотр paywall. Это не ML-прогноз покупки. Пороговые значения
задаются `ConversionPolicy`. По умолчанию cooldown семь дней, не больше двух
публикаций на родителя за 30 дней, общий максимум 100 публикаций в день,
quiet hours 20:00–09:00 timezone получателя. Safety/ожидающие вопросы имеют приоритет.

## 4. Контакт до первого сообщения родителя

Передать в `POST /parent-touch/contact-context`:

```json
{
  "parent_id": "123",
  "event_id": "5d2f9c35-a75b-4685-9bed-c229fc622ee3",
  "revision": 1,
  "observed_at": "2026-10-21T09:00:00Z",
  "valid_until": "2026-10-22T09:00:00Z",
  "language": "uz-Latn",
  "timezone": "Asia/Samarkand",
  "safety_chat_consent": false,
  "safety_push_consent": false,
  "marketing_push_consent": true
}
```

Это отдельный поток версий/UUID, не та же `revision`, что у account snapshot.
Контекст действует не более семи дней и имеет явное окончание. Для коммерческого
push нужны **оба** разрешения: актуальный `snapshot.marketing_consent` и отдельный
`contact_context.marketing_push_consent`. Safety-флаги их не заменяют; значения
в примере не подставляются всем пользователям. Backend проверяет также разрешение
устройства на уведомления. Настройки языка в двух потоках должны соответствовать
тому же подтверждённому родителю; изменение требует новых событий, не правки истории.

Parent-Touch сохраняет assistant-сообщение без выдуманного user-сообщения. Push
ссылается на уже сохранённый turn и содержит нейтральное «в чате новое сообщение»,
без детских фактов или условий покупки. Провайдерская очередь не доказывает доставку;
`unknown`/`submitting` не повторяются после перезапуска. Подробности —
[контракт proactive](mana-parent-proactive.md) и
[единый чат](mana-single-chat-integration.ru.md).

## 5. Только утверждённые предложения

Каталог задаётся владельцем в `MANA_CONVERSION_OFFERS`, не родителем/моделью
и не произвольным event payload. Полученный из billing оффер должен быть уже
доступен в штатном разделе оплаты приложения. Следующий JSON — только синтетический
пример структуры каталога, **не подтверждённая скидка для production**:

```json
[
  {
    "kind": "paid_subscription",
    "offer_id": "example-upgrade-15",
    "billing_offer_id": "example-billing-15",
    "approval_reference": "example-owner-approval",
    "valid_from": "2026-10-20T00:00:00Z",
    "valid_until": "2026-11-01T00:00:00Z",
    "currency": "USD",
    "list_price_minor": 1000,
    "price_minor": 850,
    "discount_percent": 15,
    "duration_days": 30,
    "auto_renew": false,
    "renewal_price_minor": null,
    "checkout_path": "/subscriptions/example-upgrade-15",
    "priority": 10
  },
  {
    "kind": "free_premium_days",
    "offer_id": "example-maxsus-three-days",
    "approval_reference": "example-owner-free-days-approval",
    "valid_from": "2026-10-20T00:00:00Z",
    "valid_until": "2026-11-01T00:00:00Z",
    "grant_days": 3,
    "priority": 5
  }
]
```

Цены — целые minor units: в примере 10.00 USD → 8.50 USD. Валюты текущей модели —
`UZS`/`USD`; округление скидки проверяется моделью. При `auto_renew=true` обязательна
подтверждённая `renewal_price_minor`; при `false` она `null`. `checkout_path` —
разрешённый относительный путь, не команда создать счёт. В текущем renderer родителю
предлагается открыть раздел подписок; автоматическое открытие экрана мобильным
приложением этим полем не доказано. Приоритет выбирает действующий оффер, не создаёт
динамическую цену. Бесплатные дни возможны только если `agent_trial_given=false`.

`agent-tariff-api.md` документирует исключительно
`POST /api/v1/admin-panel-payment/agent-grant-tariff/`: `parent_id` integer и
`days` 1–30, пожизненно одна non-paid выдача. Он **не** подтверждает скидку 15%,
текущий статус подписки или оплаченный переход. Агент не создаёт transaction.

## 6. Оплата и бесплатная выдача — разные исходы

После подтверждённой в штатной платёжной системе оплаты backend передаёт
`POST /conversion-agent/outcomes`. Только для действительно опубликованного
платного предложения и совпавших условий:

```json
{
  "parent_id": "123",
  "event_id": "797e088d-ec91-4bc0-8383-7a00bd99853e",
  "proposal_id": "a3cd9f41-4f6f-41db-a350-5ef790130943",
  "observed_at": "2026-10-21T09:05:00Z",
  "kind": "payment_confirmed",
  "payment_id": "example-payment-001",
  "amount_minor": 850,
  "currency": "USD",
  "billing_offer_id": "example-billing-15"
}
```

`proposal_id` берётся из фактического предложения, а не из примера. Эта структура
валидна как модель, но произвольного UUID недостаточно для успешного lifecycle.
Нужны опубликованный paid-оффер этой семьи, время после публикации и внутри срока
действия, точное совпадение суммы/валюты/`billing_offer_id`, уникальный `payment_id`.
Не заменять чек текстом «хочу купить», кликом, названием тарифа или ответом модели.
Независимо от attribution передать свежий snapshot `paid`, чтобы остановить
предложения; платежи вне конкретного оффера нельзя приписывать ему искусственно.

Обычные реакции имеют `kind="interested"`, `"declined"` или `"opted_out"`
без любых платёжных полей. Opt-out блокирует дальнейшие предложения; новый
snapshot не снимает его автоматически. Возвраты/chargeback не имеют отдельного
endpoint в текущем контракте — не выдавать их за поддержанную аналитику выручки.

Для бесплатных дней родитель сначала действительно пишет в свой чат точную
активационную фразу. Backend связывает реальный `reply_turn_id` с уже опубликованным
trial-оффером и передаёт `POST /conversion-agent/trial-acceptances`:

```json
{
  "parent_id": "123",
  "event_id": "12fdfb81-4d2d-4a20-87d1-bda847c38761",
  "proposal_id": "0cf25b5d-2fd6-477a-b3bd-7463e307a759",
  "reply_turn_id": 12,
  "confirmed_by_parent": true
}
```

Дни берутся только из замороженного каталога, не из запроса/текста модели.
Действительное подтверждение должно быть в той же семье, после оффера и не старше
15 минут. Разрешённые текущие фразы: `активировать бесплатные дни`,
`bepul kunlarni faollashtiring`, `бепул кунларни фаоллаштиринг`, `activate free days`.
Данная выдача имеет собственный durable action; unknown не повторяется новым UUID.
`granted` и `purchase_id` в квитанции agent-тарифа **не означают paid conversion**.
После неё backend обновляет правдивые free/trial факты, не посылает фиктивный
`payment_confirmed`. Платёжного API вызова здесь нет.

## 7. Почему предоставленного Parent List недостаточно

В `parent-api.md` `tariff_name`, `valid_until`, `payment_date` берутся из **текущей**
неистёкшей `TariffPurchase`, причём `is_paid` намеренно не фильтруется: бесплатный
тариф тоже активен. Поэтому эти три поля не различают free/paid. Они не возвращают
историю начала бесплатного доступа и пожизненной agent-выдачи, согласия, язык,
timezone или агрегаты активности. `children[].is_connected` — связь ребёнка,
не родительская активность и не основание для коммерческого таргетинга.

Документ содержит дублированный `/api/v1/api/v1/` в URL. В имеющемся WIP зафиксирован
ранее выполненный ограниченный тест с одним `/api/v1/`; этот документ не повторял
сетевой запрос. Новый GET статусов подписки не придуман и не объявлен существующим.
JWT login или доступ к Parent List не доказывает доступ к недокументированным полям.

Точный запрос владельцу backend:

> Нужен producer событий в уже реализованный `POST /api/v1/mana-ai/conversion-agent/events`
> либо документация реального read-only источника, из которого этот producer можно
> построить. Просьба указать: канонический `Parent.id`; авторитетные active paid/free/
> expired состояния и правило пересекающихся тарифов; реальное начало/конец бесплатного
> использования; пожизненную историю `is_agent`-выдач; отдельное marketing consent с
> датой; подтверждённые язык/timezone и push/safety permissions; датированные агрегаты
> только родительских sessions/active days/paywall views; уникальный успешный billing
> receipt с суммой/валютой/offer ID. Нужны связь с исходными таблицами/API и семантика
> каждого поля, порядок ревизий, событие отзыва/оплаты/истечения, начальный охват всех
> родителей и контроль потерь. Отдельно подтвердите действующий каталог коммерческих
> офферов и поддержку их цены штатной оплатой. Название тарифа/`payment_date` из текущего
> Parent List эту задачу не решают. Выдача бесплатных дней не является оплатой.

## 8. Открытые границы текущей реализации

- Producer/полный учёт всех реальных родителей и billing-approved каталог ещё не
  установлены. Без источника перечисленных полей цель наблюдения всех не завершена.
- Новая default-disabled ветка `MANA_CONVERSION_CONVERSATION_ENABLED` использует
  private v9: подтверждённые начало/окончание бесплатного доступа, уже истёкшего
  на момент свежего наблюдения, допускают платное приглашение в течение семи дней
  (настраиваемое окно 1–30). Само `expired` без дат недостаточно; локальные часы не
  превращают старый snapshot в подтверждение истечения. Выбирается только платный
  утверждённый оффер, срок бесплатных дней не увеличивается после окончания.
  Ранее сохранённые v7/v8 задачи/причины не обновляются автоматически. Подробности —
  [commercial checkpoint](mana-commercial-conversation-checkpoint.md).
- Нет гарантии синхронного узнавания оплаты/отзыва во внешней базе: до поступления
  свежего события локальные проверки видят только прежнее наблюдение. Нужны
  согласованные latency/интеграция producer, не обещание «проверяем live billing».
- Бесплатная выдача и дальнейший разговор не доказывают улучшение оплаченной
  конверсии. Требуются отдельные проверенные исходы; возвраты и причинный uplift
  текущим API не измеряются. Fake/MockTransport тест — не реальная доставка.
- Новые флаги выключены по умолчанию. Включение production, первичный export,
  реальный контакт и модельные расходы — отдельные согласованные шаги, не эффект
  чтения этого документа. Данные ребёнка, его GPS/переписки/страхи не используются
  для коммерческого таргетинга или давления на родителя.
